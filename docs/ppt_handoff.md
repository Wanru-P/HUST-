- 用 **Figure 10**（规模 vs 耗时）+ **Figure 11**（分区数 vs 耗时）。
- 核心数字：真实数据 314,455, 785,597, 1,569,149, 3,138,959 行四档扫描；107 次测量；测量精度（离散度中位数）12.5%（47 组，1 次预热 + 3 次计时）。
- 最值得讲的一条结论（含方法学教训）：**Parquet 的 `count(*)` 会被聚合下推到元数据层、根本不解码数据列**（全 20 列 count 0.289s vs 6 列 0.600s，列数几乎无影响）。若用 `count()` 去比较「全表扫描 vs 列裁剪」，会得出「列裁剪没有收益」的**错误结论**；改用不可下推的 `count(每列)` 后，全列 4.857s vs 6 投影列 0.600s，约 8 倍差距才显出来。
- 必须说的一句：这是 `local[N]` 单机多核，**不构成多节点横向扩展结论**；Windows 无法清 OS 文件缓存，除首次接触外扫描计时均为缓存热态。

| 挑战 | 解决方式 |

| 图迭代算法在 32GB 本机**可能**跑不完（初始风险） | 拆分：Spark 原生精确统计必完成；GraphFrames 独立脚本 + 超时看门狗 + 逐步骤落盘可续跑 —— 本次 6 个步骤全部完成 |
| MLlib 原来在训练集上自评 | 先划分、只在训练集 fit、只在测试集评估，并补简单基线 |
| 基准测试的算子设计会决定结论对错 | `count(*)` 被下推到 Parquet 元数据、不解码列 → 改用不可下推的 `count(每列)`；惰性 filter 无法减少解码量 → 规模档位改为物化子集 |
| 本地内存不足导致测量失真 | 每次测量采样可用内存，低于阈值即标记 `mem_pressure` 并单独成组，绝不与正常测量混算中位数 |

## 附：2 分钟问答准备（典型技术问题与答案）

**Q1：为什么 Gini 这么接近 1？是不是算错了？**
  不是。Gini = 0.995355 反映的是极端长尾：43.54% 的模型下载为 0，而头部极少数模型下载量以亿计。我们用三种等价口径互相验证（秩式 / 频数加权 / Lorenz 梯形积分），最大绝对差在 1e-12 量级；并且用 300 组随机数组与朴素两两差定义做了对照。

**Q2：为什么不直接说这是幂律分布？**
  因为幂律需要严格的分布拟合与模型比较（例如与对数正态、指数做似然比检验）。我们只观察到 Lorenz 曲线显著偏离对角线与 CCDF 双对数近似直线，这只能说明「长尾」，不足以证明「幂律」。

**Q3：下载量能代表模型质量吗？**
  不能。下载量只反映传播热度，受曝光、营销、上游底座热度等影响。本报告全文避免用「质量」描述下载热度，也不把 PageRank 等同于质量。

**Q4：训练/测试怎么保证没有泄漏？**
  先在 626,269 行建模样本上按 seed=42 做 8:2 划分，one-hot 词表与 Top-50 库词表都只在训练集上 fit，特征中不含任何由目标派生出来的量，并显式检查 train∩test = 0。

**Q5：为什么 R² 不高？**
  因为下载量是极端长尾的，且受快照时间点影响很大。RQ4 的目标本来就是「刻画统计关联」而不是「追求预测精度」；我们同时给出简单基线作为参照，避免只报一个看起来很高的数字。

**Q6：GraphFrames 到底跑完了吗？**
  实际状态是 `completed` —— 6 个迭代步骤全部完成。这不是预算内的推测：每个步骤的耗时都是真实测量值，完整边表（未抽样）与全部 Spark 可计算的图统计也都保留着。回答这类问题要区分三层：**初始风险**（迭代算法在大图上开销高）、**应对策略**（独立脚本 + 超时看门狗 + 逐步骤落盘可续跑）、**最终状态**（全部完成）。**NetworkX 只用于小规模验证与可视化，绝不冒充 GraphFrames。**

**Q7：为什么用 local[6] 而不是 local[16]？**
  本机 32 GB 物理内存实际可用远小于 32 GB，且需要保留其他程序正常运行。我们从 local[4]/local[8] 起步做并行度扫描，选择在内存峰值可控的前提下完成全量 ETL 的配置，并且从不默认「核数越多越快」。

**Q8：别人能复现吗？**
  可以。工程提供固定版本的依赖、环境变量说明、完整执行顺序、以及从 Bronze 出发的复现步骤；**不需要重新下载 314 万条模型明细**，只需 `models.parquet` 一个文件（有 SHA-256 校验）。详见 `docs/final_acceptance.md` 的可复现性一节。

**Q9：家族谱系为什么不直接当树来处理？**
  因为数据本身不是树。血缘边是**有向**的（底座 → 衍生），且实测有 15,047 个衍生模型有**多个底座**（合并），底座之间也可能互相指向。若强行按树处理，要么丢掉合并边、要么制造出并不存在的父子关系。我们保留完整的有向图与多父拓扑，只在计算「深度」时做必要的图算法处理。

**Q10：图里有环，那「最长衍生链」怎么算？不会算错吗？**
  这正是我们特意处理的地方。含环的有向图上，「最长路径」**没有定义**（最长简单路径是 NP-hard）。所以先求**强连通分量（SCC）**，把每个环折叠成一个超级节点，得到一张**凝聚 DAG**，再在它上面求最长路径。实测真正落入环中的节点只有 24 个、自环边 2,060 条，规模很小，但流程上必须做，否则结论不成立。

**Q11：那个交互式探索器展示的是全部家族吗？**
  **不是。** 页面上是**有界子图**：只包含按直接衍生数排名的 Top-N 家族的直接子节点，以及三个案例家族的 2 跳，并且有节点/边数上限，超出就截断。页面上有显式的截断提示。它用于**交互式理解结构**，所有量化结论仍然取自全量计算结果。

**Q12：Theil 分解说明了什么？**
  它把总体不均衡拆成「组间」和「组内」两部分。我们的结果是**组内占比远高于组间** —— 也就是说，即使按任务类型、创建年份、或有无血缘把模型分组，**每一组内部仍然是极端长尾的**。这不是推翻 RQ2，而是对「不均衡来自哪里」的一个更细的解释。
