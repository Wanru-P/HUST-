## 0. 实验设计与口径纪律

| 项 | 设置 |
| --- | --- |
| Spark Master | local[6] |
| 数据来源（主实验） | `data_hubstats/bronze/models.parquet`（真实 hub-stats 快照） |
| 规模档位 | real_100pct, real_10pct, real_25pct, real_50pct, real_cold_touch |
| 对应行数 | 314,455, 785,597, 1,569,149, 3,138,959 |
| 算子 | etl_pipeline, explode_tags, filter, graph_edges, groupby, join, parquet_scan_first_touch, parquet_scan_full, parquet_scan_projected, parquet_scan_scaled |
| 重复次数 | 每个 (规模, 分区数, 算子) 组合 1 次不计时预热 + 3 次计时，报告**中位数** |
| 分区扫描 | 16 / 32 / 64，其余条件（数据、算子、master、driver 内存）全部固定 |
| 规模扫描组 run_tag | real_local6_dm3g |

**选样方法**：`crc32(id) % 100 < pct`。同一 hash 阈值意味着 10% ⊂ 25% ⊂ 50% ⊂ 100%（**嵌套子集**，不是独立抽样），因此各档之间的差异只来自数据量，不来自样本构成变化；且计算逻辑在各档完全一致。该哈希与 Python 侧 `zlib.crc32` 完全等价（由 `test_spark_contracts.py` 在真实 model_id 上交叉验证），所以 Spark 路径与本地路径选中的是**同一批行**。

**规模档必须物化，不能对惰性 filter 计时**：Spark 的 Parquet 向量化读取是「整批解码所需列、再应用过滤」，而 `pmod(crc32(id),100)<10` 属于函数谓词，Spark 的 record-level filter 只认顶层列的简单比较、识别不了它，于是过滤列以外的列**仍为整批行解码**、过滤后才丢弃。实测在 10% 子集上强制解码全部 20 列要 5.411s，与 100% 全表的 5.096s 几乎相同。因此本实验先把各档物化成独立 Parquet 文件再计时，否则每个规模档都会白付一次全表扫描成本，「耗时随规模变化」的结论会失真。

**Parquet 扫描算子必须用不可下推的聚合**：Spark 对 Parquet 的 `count(*)` 会**聚合下推到元数据层**，完全不解码数据列 —— 实测 3,138,959 行下全 20 列 `count()` 0.289s、6 列 `count()` 0.600s，而真正解码全 20 列要 4.857s。若用 `count()` 比较「全表扫描 vs 列裁剪」，两者耗时几乎相同，据此写「列式存储列裁剪优势」就是**编造结论**。因此扫描类算子统一改用 `count(每列)`（不在 Spark 的 Parquet 聚合下推支持列表内，会真正逐行解码，且几乎不引入额外 CPU），`parquet_scan_full` 解码全部 20 列、`parquet_scan_projected` 只解码 6 个投影列，两者聚合形式完全一致，差异只来自列集合。

**缓存口径**：

- 计时区域内**不使用** `cache()/persist()`，因此不存在「拿缓存命中结果与冷读结果直接比较」；
- Windows 没有可用接口清空操作系统文件缓存，因此除 `parquet_scan_first_touch`（本进程首次接触该文件）外，所有扫描计时都发生在 OS page cache 已热的状态下，报告里已逐行标注；
- 每档都先做 1 次不计时的预热，再取 3 次的中位数。

**指标可用性纪律**：`shuffle_read_bytes` / `shuffle_write_bytes` / `executor_run_ms` 取自 Spark UI REST 接口的 stage 级累计值（本地模式下 StatusTracker 在 action 结束后取不到已完成 stage 的 taskMetrics）。**确实取不到时记为「不可用」并在汇总中排除，绝不写 0** —— 写 0 等于谎称该算子没有发生 shuffle。同时关闭 AQE，因为 AQE 会把已物化的 shuffle stage 标成 `SKIPPED`，使其指标恒为 0，会系统性低估 shuffle 量。

**内存压力必须显式标注**：每次测量的计时窗口内会采样系统可用物理内存，若最低值低于 0.80 GiB，该行 `mem_pressure` 记为 true 并**在汇总里单独成组**，不与正常测量混算中位数。本机实测：`-Xmx3g` 时 Spark JVM 的 RSS 峰值可达 6.18 GiB，会把可用内存吃到 0.004 GiB，导致 100% 档的重算子发生换页、耗时不可复现。因此正式运行把 driver 内存降到 `['3g']`。本次运行共 0 个组合被标记为内存压力（见 §3.2），**未参与 §1/§2 的对比**。

**命名纪律**：本机是 `local[N]` 单机多核，实验只能说明**本地并行度与资源对耗时的影响**，**不得**表述为多节点横向扩展。

**合成数据**：`--mode synth` 的结果单独存放、单独标注为 `synthetic_stress_test`，只用于受控压力测试，**不得**用于任何 Hugging Face 生态结论。（原实现的合成数据存在「整列常量」的缺陷，现已改为取值逐行变化。）

## 4. 结论要点

- **执行时间随数据规模增长**：见 §1 的表格，各算子在 10%→100% 之间增长；由于各档已物化成独立 Parquet 文件，增长只反映数据量，不含固定的全表扫描成本。
- **分区数不是越多越好**：见 §2。分区数过小时单分区数据量过大、易 spill；过多时调度与 task 启动开销上升。本机最优点应结合具体算子看，不能一概而论，也不能把 `local[16]` 当成默认最优。
- **Parquet 列裁剪确实有效，但必须用不解码列的方法测不出来**：`count(*)` 会被聚合下推到 Parquet 元数据层（全 20 列 0.289s vs 6 列 0.600s，列数几乎没有影响），只有改用不可下推的 `count(每列)` 才能真正解码；此时全 20 列 4.857s vs 6 投影列 0.600s（约 8 倍），列裁剪收益才可测。这本身也是一条工程结论：**基准测试的算子设计错了，会得出完全相反的结论**。
- **shuffle 是主要瓶颈**：见 §3，shuffle 读/写量大的算子（`etl_pipeline`、`groupby`）耗时显著更高；这与「减少 shuffle、避免全局排序」的工程优化方向一致。注意 `count()` 本身也会产生一个两阶段的 shuffle（部分计数 + 最终合并），因此扫描类算子并非零 shuffle。
- **全局排序与数据倾斜是风险点**：Phase 1B 已把下载量分布统计从「无 partitionBy 的全局窗口排序」改成「频数聚合 + 组内并行排名」，消除了 314 万行被压到单分区串行处理的瓶颈（见 `docs/full_etl_report.md`）。
- **局部性与缓存**：本机所有测量都在 OS 文件缓存已热的状态下取得（`parquet_scan_first_touch` 除外），因此扫描耗时偏乐观，已在报告中标注。
