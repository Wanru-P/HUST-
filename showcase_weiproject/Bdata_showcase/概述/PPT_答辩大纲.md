# 《开源 AI 模型生态分析》· 讲给大二同学听（PPT 大纲）

> **场景**：你是计算机专业大二学生，在课堂 / 小组分享里，给**同样是计算机专业的大二同学**讲你做的这个大数据项目。
> 所以——**不用端架子，不用背术语，用"同学讲给同学"的方式，把事说明白就行**。
> 目标时长 **12–15 分钟**，共 **20 页**；⭐ = 重点页，🔧 = 时间紧可跳过的页。
> 每页都给你：一句话核心 / PPT 标题 / 版面怎么排 / 内容怎么写（带程序员梗）/ 怎么开口讲 / 怎么过渡。

---

## 一、开场先定个调：你不是在"汇报"，是在"给同学安利"

- **语气**：像跟室友讲"我昨晚熬夜跑出来的东西"那样，轻松、带点梗，但不瞎吹。
- **姿态**：平等交流，多用"咱们""你""大家"，少用"本报告""我们发现"这种书面腔。
- **能用的程序员梗**（同学秒懂，别滥用，一页最多一个）：
  - GitHub 的 fork / star、祖传代码、祖师爷、徒子徒孙
  - 报错红屏、Stack Overflow、CV 工程师（复制粘贴）
  - 炼丹（AI 训练）、调参玄学、跑通了
  - Spark 是"懒"的、shuffle 是"倒数据"、单分区是"一个人干十个人的活"
  - 二八定律（其实这里比二八还夸张）

**你整场要让同学记住的一句话**：
> 「我拿 Spark 处理了 314 万行开源模型数据，发现这个生态比咱们想的更"卷"——1% 的模型拿走了 97% 的下载，模型之间还互相"抄作业"。」

## 二、编排总原则

### 2.1 时间怎么分（15 分钟）

| 章节 | 页码 | 时长 | 讲法 |
| --- | --- | --- | --- |
| 开场 + 问题 | 1–4 | 2.5 min | 抛钩子，让同学好奇 |
| 数据与方法 | 5–7 | 3 min | 讲清"我怎么折腾这些数据" |
| 技术难点 | 8–10 | 3 min | 讲踩坑，最容易引起共鸣 |
| 结果 | 11–16 | 5 min | 一句结论 + 一张图，节奏快 |
| 创新 + 总结 | 17–20 | 1.5 min | 收口，留提问 |

### 2.2 给同学讲的三条铁律
1. **每页只讲一件事**，讲完就翻页，别恋战。
2. **先抛结论，再上图**——同学先知道"所以呢"，再看图才不迷糊。
3. **一页一个梗就够**，梗是调味料，不是主菜；技术数字还是得真实准确。

### 2.3 演讲者备注（一定要用）
- 把每页"怎么开口讲"那段粘进 PPT 的**演讲者备注**，放映时用"演示者视图"，只有你自己看得到。
- 手边备一张**数字速查卡**（文末附录），同学突然问"具体多少"时瞄一眼。

### Slide 3 · 研究背景与动机 —— 60 秒，用"GitHub"讲

- **一句话核心**：开源模型社区就像巨型 GitHub，但没人算过它的"卷"。
- **PPT 大标题**：GitHub 有 314 万个仓库，Hugging Face 有 314 万个模型
- **版面**：左边放增长曲线（`fig01_monthly_evolution.png`），右边三个现象小图标：头部独大（一个金杯）/ 互相 fork（一棵树）/ 冷热不均（几个分叉）。
- **内容怎么写（大白话 + 梗）**：
  - Hugging Face 是全球最大的开源模型社区，模型数已经超 314 万，还在暴涨。
  - 但这个社区里有三件事没人系统算过：**头部几个模型拿走绝大多数下载、模型像 GitHub 一样互相 fork、不同任务冷热差老远**。
  - 于是我想：能不能用上课学的 Spark，把这三点量化出来？
- **怎么开口讲**：「咱们都知道 GitHub 上热门仓库 star 数能碾压冷门仓库。Hugging Face 上的模型也是这样吗？我就想用数据实锤一下。」
- **过渡语**：「为了说清楚，我拆成 5 个小问题。」

### Slide 4 · 研究问题（5 个 RQ）—— 40 秒，一张表带过

- **版面**：5 行表格（问题 / 方法 / 大白话），每行配个迷你图标。
- **内容怎么写**：
  | RQ | 问题（大白话） | 方法 |

  | RQ1 | 模型一年年怎么涨起来的？ | 时间序列统计 |

### Slide 5 · 数据来源与规模（4V）⭐ —— 90 秒，重点页

- **一句话核心**：数据够大、够杂、还有点脏，但我都处理了。
- **PPT 大标题**：314 万行数据，从哪来、多大、多"脏"
- **版面**：中间一个大数字 `3,138,954`，四周四个 "V" 图标围一圈。
- **内容怎么写（每个 V 一句程序员能懂的话）**：
  - **Volume（大）**：3,138,954 个去重模型，源文件 1.49 GiB——「比 GitHub 上一个中型 monorepo 还大」。
  - **Variety（杂）**：有数字、有嵌套 struct、有标签数组、还有"底座关系"这种关系字段——「不是一张干净的表，是各种类型混着来」。
  - **Velocity（快）**：带"近 30 天下载"这种滚动窗口——「数据是活的，天天变」。
  - **Veracity（脏）**：任务标签缺 65.6%、底座关系缺 71.7%——「我没瞎填 NULL，是显式标出来单独算」。
- **版面细节**：数据源一行小字 `cfahlgren1/hub-stats`，旁边打一个绿色徽章 "SHA-256 校验通过 ✓"。
- **怎么开口讲**：「数据从 Hugging Face 官方数据集来的，我固定了提交版本、做了 SHA-256 校验，不会跑着跑着数据变了。而且它 65% 的任务标签是空的——这数据比咱们课程实验的数据脏多了，但我没瞎填。」
- **过渡语**：「这么杂的数据怎么加工？我用了一个"做菜式"的三层架构。」

### Slide 6 · 技术架构（Medallion 三层）⭐ —— 60 秒

- **一句话核心**：三层漏斗，每层都能单独验证、可追溯。
- **PPT 大标题**：Bronze → Silver → Gold，像做菜一样层层加工
- **版面**：三层漏斗，每层旁标注类比 + 行数：
  - **Bronze（原料）**：原始 parquet，3,138,959 行——「刚买回来的食材，原样入库」。
  - **Silver（洗切配）**：去重 + 展开标签/血缘，主表 3,138,954 行、标签 2063 万、血缘边 92 万——「洗干净、切好、分装」。
  - **Gold（上桌成品）**：7 张分析表 + 集中度统计表——「直接能吃的菜」。
- **版面细节**：漏斗右侧列技术栈小图标：PySpark 4.2.0 / GraphFrames 0.12.3 / MLlib / Python 3.11 / Java 17。
- **怎么开口讲**：「为啥分三层？因为每一步都能单独验证，出错了能定位到是哪一层，而不是一锅端——就像写代码分层解耦，哪层崩了报错就报哪层。」
- **过渡语**：「光有架构不够，关键是整条流水线能一键重跑。」

### Slide 7 · 数据流水线（可复现）🔧 —— 40 秒，可快讲

- **一句话核心**：一条命令链 + 一个"唯一事实来源"，数字绝不打架。
- **PPT 大标题**：一键重跑，数字只来自一个地方
- **版面**：横向流水线，节点连箭头：`下载 → ETL → 验证 → 5 个分析 → 图算法 → 出图 → 结果清单 → 一致性检查`，末尾高亮 `results_manifest.json`。
- **内容怎么写**：
  - 34 个 Python 脚本串成一条链，一条命令能从头跑到尾。
  - 所有报告、图、看板的数字**都从同一个结果清单读**——「一处改处处改，不会出现两个版本的数对不上」。
  - Spark 和 pandas 两条引擎结果分目录隔离，互不覆盖——「就像 main 分支和实验分支，不互相污染」。
- **怎么开口讲**：「我最得意的点：所有数字只有一个来源，报告、图、看板都读它，所以数字绝不会自相矛盾。这是我觉得比'跑通'更重要的地方。」
- **过渡语**：「听着顺利，其实踩了一堆坑，我挑几个最狠的讲。」

### Slide 8 · 难点总览（踩坑地图）🔧 —— 30 秒，可快讲

- **一句话核心**：证明你不只是"跑通了 Demo"，是真踩过坑。
- **版面**：2×4 卡片墙，每张 = 坑名 + 一句"我怎么填的"：

  2. 新数据源 Schema 变了 → 写适配层统一类型
  3. 时区陷阱 → 全局锁 UTC
  4. 全局排序卡死 → 用频数表降维
  5. 93 万节点图跑不动 → 拆脚本 + 看门狗 + 续跑
  6. ML 评估泄漏 → 先切训练/测试
  7. 32GB 内存不够 → 按需调并行度
- **怎么开口讲**：「这七个坑，每个都能讲十分钟，我挑最体现'排查能力'的一个展开——很多同学在 Windows 上跑 Spark 都会撞它。」
- **过渡语**：「先说第一个，Windows 上跑 Spark 的祖传报错。」

### Slide 9 · 难点深挖：Windows 上跑 Spark ⭐ —— 90 秒，全场共鸣点

- **一句话核心**：Spark 在 Windows 上要"管文件权限"但没有工具，我用不折腾的方式绕过去了。
- **PPT 大标题**：为什么别人在 Windows 跑 Spark 总报错，我没报？
- **版面**：左右两栏——左边"坑"（红色，配报错/死锁示意），右边"解法"（绿色，三条）：
  - 坑：Spark 默认的 `RawLocalFileSystem.setPermission` 在 Windows 上只有两条路——要么原生库 `hadoop.dll`，要么 `winutils.exe`，而 `core-default.xml` **没有任何开关能关掉这次调用**（我反编译 Hadoop 源码才确认的，不是查百度查出来的）。
  - 解法①：换纯 Java 的 `BareLocalFileSystem`，它的 `setPermission` 在 Windows 上直接空操作，不碰原生库、不碰外部进程。
  - 解法②：时区必须锁 UTC，否则 23 点的 UTC 记录会被推到下个月——「一个小时的时差能把数据归错月份」。
  - 解法③：全局排序改"先聚合频数表、再查表还原排名"，绕开单分区 shuffle——「别让一个人干十个人的活」。
- **怎么开口讲**：「我当时也不信没法配，就反编译了 Hadoop 的 jar 一行行看，确认它真没留开关。于是我不硬刚，直接换一个行为正确的实现。这段排查经历，我觉得比代码本身更值。」
- **过渡语**：「工程跑通了，还得证明'数字是对的'。」

### Slide 10 · 算法正确性 ⭐ —— 60 秒，讲"数字凭什么可信"

- **一句话核心**：Gini 不是估的，是精确算的，还用三套算法互相验证。
- **PPT 大标题**：你的 Gini 准吗？我写三套算法交叉验证，误差 0.0000000000000004
- **版面**：上方一条"等价性证明"小表格（三种口径 → 结果 → 偏差），下方绿色对勾瀑布：`56 项契约测试 ✓`、`114 项一致性检查 ✓`。
- **内容怎么写**：
  - Gini 用**频数加权秩公式**精确计算，不是采样近似。
  - 三种独立口径（秩式 / 频数加权 / Lorenz 梯形积分）结果一致，最大偏差 ≤ 4.4e-16——「就是浮点误差的量级」。
  - 两种下载口径严格区分：近 30 天 vs 历史累计，相差 27 倍，绝不混着用。
- **怎么开口讲**：「有人可能会问'你这数字靠谱吗'。我的回答是：我写了三套互相独立的算法，结果在小数点后 15 位才差一点点，那就是浮点误差，说明算对了。而且我区分了两种下载口径，差 27 倍，混着用就是耍流氓。」
- **过渡语**：「方法讲完了，直接上结果，每页一句结论 + 一张图。」

### Slide 11 · RQ1 生态演化 ⭐ —— 50 秒，先甩结论

- **一句话核心**：生态在 2024 年 9 月达到巅峰，之后还在涨。
- **PPT 大标题**：2024 年 9 月，开源模型"大爆发"
- **版面**：左边大字 `峰值月 2024-09 · 新增 125,030 个`，右边放 `fig01_monthly_evolution.png`。
- **内容怎么写（大白话）**：
  - 一年比一年多：2022 年 10 万 → 2023 年 31.8 万 → 2024 年 74 万 → 2025 年 110 万。
  - 「就像 GitHub 上开源仓库数量，一年翻一倍多，大家都往上传模型。」
  - 诚实交代：任务标签缺 65.6%，首月有时间戳异常，我单独说明、不硬解释。
- **怎么开口讲**：「第一个结论——生态在 2024 年 9 月达到单月新增 12.5 万个的峰值。但我坦白，最早那个月的数据有时间戳异常，我不瞎编原因，只当它是观测现象。」
- **过渡语**：「模型这么多，下载量是平均分吗？答案是——差老远了。」

### Slide 12 · RQ2 注意力集中与长尾 ⭐ —— 60 秒，全场最震撼

- **一句话核心**：下载的"贫富差距"大到离谱，1% 拿走 97%。
- **PPT 大标题**：1% 的模型，拿走了 97% 的下载
- **版面**：左边放 `fig05_lorenz.png`，右边放 `fig06_ccdf_longtail.png`，顶部一行大字 Gini = 0.995。
- **内容怎么写（用同学秒懂的话）**：
  - Gini（近 30 天）= 0.995，Top-1% 拿走 97.13%；Gini（累计）= 0.998，Top-1% 拿走 98.70%。
  - 「咱们常说'二八定律'，这里比二八还狠——是'一九九八'：1% 头部拿走近乎全部，剩下 99% 分那一点。」
  - 43% 的模型**零下载**——「相当于你辛苦上传了个模型，结果一个人都没下，像给 GitHub 空仓库 push 了个寂寞。」
  - 严谨声明：我只描述长尾形态，不宣称它一定是幂律（没做严格拟合）。
- **怎么开口讲**：「第二个结论最震撼——Gini 系数 0.995，几乎到 1。1% 的头部模型拿走 97% 的下载，剩下 99% 的模型抢那 3%。而且 43% 的模型下载量是 0。」
- **过渡语**：「既然头部这么吃香，这些头部之间是什么关系？就是谱系网络。」

### Slide 13 · RQ3 模型谱系网络 ⭐ —— 70 秒，用"fork/祖师爷"讲

- **一句话核心**：模型像 GitHub 一样互相 fork，FLUX.1-dev 是最大"祖师爷"。
- **PPT 大标题**：模型界的 fork 链：一个底座，生出 4 万多个"徒子徒孙"
- **版面**：左边放 `fig07_family_network.png`，右边列关键数字卡片。
- **内容怎么写（大白话 + 梗）**：
  - 血缘边 919,839 条，节点 931,066 个——「一张 93 万节点的'fork 关系图'」。
  - 最大底座 `FLUX.1-dev` 直接派生 **43,419** 个模型——「一个祖师爷，四万多个 fork 它的项目」。
  - 关系四种：finetune（微调）、adapter（加适配器）、quantized（量化压缩）、merge（合并）——「就像 fork 之后要么改、要么合并、要么加插件」。
  - 图算法 6 步全跑完：连通分量 42,890 个（图内）、PageRank 双向、标签传播 126,431 个社区——「图论课学的连通分量、PageRank，这次真用上了」。
- **怎么开口讲**（补一个严谨细节）：「数节点时不能把'底座数 + 衍生数'直接相加，因为一个模型可能既当别人的底座、又当别人的衍生，直接加会重复算 4 万多个。我取的是去重并集 93 万——这个坑估计不少同学会掉。」
- **过渡语**：「那什么样的模型更容易'火'？我用机器学习找关联——先说好，是关联，不是算命。」

### Slide 14 · RQ4 统计关联（MLlib）⭐ —— 70 秒，讲"防作弊"

- **一句话核心**：标签越丰富、选对库，越可能"火"；但我保证没"作弊"。
- **PPT 大标题**：什么让模型更"火"？标签数量排第一
- **版面**：左边放 `fig09_ml_importance.png`，右边放模型对比小表格。
- **内容怎么写（大白话）**：
  - 目标：预测 `log1p(下载量)`；先切训练/测试（seed=42，两者零交集），**绝不拿测试题练手**。
  - 结果：RandomForest 的 R²=0.663，比 LinearRegression(0.418) 和 GBT(0.631) 都好——「随机森林这个'炼丹'配方赢麻了」。
  - 最重要特征：`tag_count`（标签数量）0.413 > `library_top`（用什么库）0.194 > `likes_log`（点赞）0.151。
  - 诚实定位：点赞和下载是同一时刻的数据，**重要性 ≠ 因果 ≠ 预测未来**。
- **怎么开口讲**：「我特意防了'评估泄漏'——就像考试不能拿测试卷当练习题。先切好训练集和测试集，模型只在训练集练、只在测试集打分。结果标签数量是最强关联特征：标签写得越全，越容易被发现。」
