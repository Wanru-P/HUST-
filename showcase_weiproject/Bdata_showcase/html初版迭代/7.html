PART 01 / 问题与数据

研究背景：为什么要研究 Hugging Face 生态

平台现状

  • 规模空前：Hub 上公开模型已超过 314 万，是全球最大的开放模型托管平台
  • 生态复杂：模型之间存在底座—衍生的血缘关系，形成庞大谱系网络
  • 注意力失衡：下载量呈极端长尾，少数头部模型占据压倒性份额
  • 结构盲区：平台提供搜索与下载，但不提供生态结构性的量化刻画

研究缺口

现有研究多聚焦单个模型性能，缺少对整个平台生态结构的大数据刻画。 具体来说，三个层面此前没有系统性回答：

  • 时间维度：模型发布速度、任务分布如何随时间迁移？
  • 分配维度：下载注意力集中到什么程度？集中度来源在哪？
  • 关系维度：模型之间的血缘网络是什么形状？
💡 本项目把 Hugging Face Hub 当作一个"超大规模社会系统"来研究——不是看单个模型，而是看整个生态的结构与演化。

PART 01 / 问题与数据

Windows 环境适配：三个典型坑与对策

坑 1

winutils.exe 缺失

Spark 在 Windows 上依赖 Hadoop 的 winutils.exe， 官方不提供，网上流传的二进制版本常与 Hadoop 版本不匹配。

✅ 对策：使用 hadoop-bare-naked-local-fs —— 纯 Java 实现的本地文件系统，完全绕过 winutils。
坑 2

时区漂移

本机时区与 UTC 不一致时，跨月边界的时间戳会平移， 导致月度统计对不上。

✅ 对策：锁定 UTC 时区， 所有时间解析统一在 UTC 下进行。
坑 3

内存压力

314 万行全量 join + 图构建时 driver 容易 OOM， 但调太大又会压垮开发机。

✅ 对策：driver 锁 3g， 配内存告警 + mem_pressure 标记隔离， 超限步骤单独跑。
📌 这三条经验都具有通用性，可作为"Windows 上跑 Spark"的可复用工程模板。

PART 02 / 核心发现

RQ2下载注意力的极端集中

洛伦兹曲线 · Lorenz Curve
曲线越向下弯曲，集中度越高。当前曲线严重偏离对角线。

核心结论

  • 极端长尾：绝大部分模型下载量极低，头部模型占据压倒性份额
  • 基尼系数高：洛伦兹曲线严重偏离对角线
  • 幂律特征：下载分布不符合正态，而是典型的重尾分布
  • 生态含义：注意力高度集中在少数"明星模型"上

为什么用洛伦兹曲线

洛伦兹曲线是经济学衡量收入不平等的标准工具，横轴是人口累积占比， 纵轴是收入累积占比。我们把它迁移到"下载注意力"的分配问题上—— 横轴是模型累积占比，纵轴是下载量累积占比。 对角线 = 完全平均，越弯 = 越集中。

可比性判定（关键设计）

comparable = true 表示有资格参与跨任务比较， 而不是"样本量够大"这么简单。判定条件：

  • n_models ≥ 200 —— 样本量门槛
  • distinct_values ≥ 20 —— 属性多样性门槛

⚠️ unknown 恒为 false

pipeline_tag 缺失统一记 unknown（约 65.6%）， 绝不参与任何跨任务排名——否则会人为制造一个"最大类别"。

PART 03 / 工程亮点

工程亮点：可复现性与工程纪律

固定快照

权威来源唯一

commit + SHA-256 双重校验；所有结果以 results_manifest.json 为权威来源。

引擎隔离

产物互不覆盖

spark 与 local 两套引擎产物落在不同目录，切换引擎不会污染已有结果。

资源约束

两重保护

driver 内存锁 3g，配内存告警 + mem_pressure 标记隔离超限步骤。

规模档哨兵

real_cold_touch 行数比 100% 档还多 5 行，按"至少两个分区档中取行数最大者"统一挑选，避免哨兵行误判。

指标诚实性

shuffle / CPU 指标取不到记空值，绝不写 0；关闭 AQE 以避免 shuffle 被系统性低估。

12 图完整性守卫

缺任何一张图即退出码 1；增量图（Fig13–15）输出到独立目录，不污染旧守卫。

📌 这些设计让项目不只是"跑出了结果"，而是"结果可信、可复现、可审计"。
